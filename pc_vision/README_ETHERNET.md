## R15 传输架构与原有验证

2026-10-30：已准备 ARM 网口服务、电脑 GPU 接收/跟踪/结果回传、可选 HDMI 编号 RTL 源码。
本轮没有连接 PYNQ、串口、JTAG 或 hardware server，没有下载或烧录，也没有修改网卡或防火墙。
R14 只读恢复包和 R13/R14 原 ELF 保持原 SHA256。新增 ELF 单独命名为候选版。

## 数据链路与现有功能

```text
OV5640 -> 原 FPGA 采集/图像处理 -> HDMI 640x480
                  |
                  +-> 已有冻结分析帧 320x240 RGB565
                         -> ARM GEM0 / lwIP UDP -> 网线 -> PC CUDA
                         <- 帧号 + 时间戳 + 编号 + 目标框 <- YOLOv5su + ByteTrack
                         -> 原叠加邮箱/ACK -> HDMI 与 UART/网页目标状态
```

- 摄像头、扩展板信号线保持原接法；本方案新增主板 RJ45 网线连接电脑。
- 传图复用稳定的 320x240 分析缓冲区，复制后分片发送，避免读取正在变化的 VGA DDR 帧。
  **网口输入目前不是 640x480 或 500 万像素。** HDMI 仍为 640x480；预览放大不增加细节。
- 电脑处理所有可见车辆轨迹；受现有硬件邮箱限制，回传最多 8 个框。
  优先保留已选目标，明显更大的新目标可替换小目标；面积只用于选择显示名额，不表示实测距离。
- 跟踪包含 car、motorcycle、bus、truck；使用 YOLOv5su COCO 权重，非 TomMao PSP/Lab 模型。
  当前没有语义分割、真实车速或违章判定。
- 已保留交通灯、倒计时、ToF、姿态、环境、小屏、图像模式、网页同步和拍照相关代码。
  网线候选版使用 GPU 框替代原帧差框；断线时清框，不能把旧框当成仍检测到车辆。
  其余功能与新网口的整机并行性能仍需未来板上回归。

## 本次优化

1. UDP 每片 48 字节头、最多 1344 字节数据；MTU1500 下不依赖 IP 分片。
   CRC32 检查、乱序重组、重复片处理、缺片超时，避免拼接不同帧。
2. 只保留一个待拼帧和一个最新完整帧，GPU 忙时丢旧帧，避免排队累积延迟。
   ARM 分时轮询收发，不等待网线插入或协商完成，不注册新的网口中断。
3. 帧携带会话、控制代号、源帧号和采集时间。开发板拒绝未发出的、旧会话、重复、倒序和超龄结果。
   关闭识别、拍照暂停、断线会清除旧框；快速关闭再开启也拒绝开启前的采样结果。
4. ByteTrack 按采集时间推进预测，适应变帧率和丢帧；新轨迹可正常确认。
   短时遮挡保留关联历史约 2 秒，可见后尝试恢复编号，漏检期间不画虚构预测框。
5. 最近 700ms 的置信加权类别投票减少 car/truck 标签跳变，编号在电脑与回传结果中一致。
   密集画面使用紧凑标签，小框只标编号，完整类别保存在 JSON 中。

超时设置是代码策略，**不是实测端到端延迟承诺**。持续遮挡、相似车辆交叉、检测漏检仍可能换号。

## 将来有网线后的配置与启动

这里只提供步骤；本轮未执行以下真实连接操作。

1. 电脑有线网卡配置 `192.168.2.1 / 255.255.255.0`，主板固件静态地址 `192.168.2.99`。
   网关可留空；避免与其他网卡已有子网冲突。电脑若已有合适的固定 IP，也可修改
   `firmware/src/pc_net_config.h` 后重新构建候选 ELF，同时匹配下方启动参数。
2. 接主板 RJ45 与电脑网口；硬件烧录须另行按用户后续指令执行。
   网络默认 UDP：主板 `50010`，电脑 `50011`。只在确有阻拦时为对应程序/私有网段配置放行规则，脚本不会自动修改防火墙。
3. 使用已有项目 Python 环境 `.venv`、CUDA 和 `models/yolov5su.pt`，在本目录运行：

```powershell
powershell -File .\run_ethernet.ps1
# 地址不同：
powershell -File .\run_ethernet.ps1 -Board 192.168.2.99 -Bind 192.168.2.1
```

该脚本会主动联系指定主板，但没有烧录命令。按 ESC 关闭预览。
默认输出 `runs/ethernet_live/state.json` 和 `latest.jpg`。
电脑 JSON 中 `objects` 是回传的最多 8 个目标，`all_objects` 是所有可见目标；
`hdmi_acknowledged:false` 表示电脑发出结果不等于 HDMI 已接收。
原 UART 网页通道仍以硬件邮箱 ACK 后的状态为准。

## 构建与 HDMI 编号兼容性

```powershell

powershell -File ..\verification\build_pc_network.ps1
```

输出：`firmware/release/vehicle_assist_pcnet_r15_candidate.elf`。

没有改动 Vivado 工程、PS7 初始化、引脚或正式 BIT/XSA。
候选构建默认 ToF、遥测、网页控制、4 秒拍照稳定等待均开启，实验 ToF soft-reset 关闭。

- 现有 OB01 硬件：可接收绿框，电脑/网页有编号，**HDMI 不显示编号文字**。
- `../rtl/camera_obstacle_overlay.v` 与 `../rtl/axi_pl_hub.v` 是 OB02 候选源文件，支持 16 位编号，显示五位数字。
  仅在将来重新生成配套硬件时替换对应两个源模块；其余硬件源码继续使用原工程。
  ARM 自动识别 OB01/OB02，对旧硬件不发送编号占用位。
- OB02 已通过 xvlog 语法检查和 C 侧打包测试；本机 xelab 所带 GCC6.2 出现 Windows 系统 DLL 重定位错误，
  本轮没有完成像素仿真、综合、布线或时序收敛，**没有新的 OB02 BIT/XSA**。
  将来构建硬件时必须确保 BIT、XSA、PS7 来自同一轮；不可仅凭候选 ELF 宣称 HDMI 编号已在板上生效。

## 离线证据

结果位于 `runs/r15_udp_final_20261030/` 与 `validation/网线目标跟踪R15离线验证.md`：

- 用户原视频按 10Hz 取样、降采样至 320x240 并量化为 RGB565，然后经过真实协议打包/乱序/重复/丢包模拟，再进行 CUDA 检测和编号跟踪。
- 246 个取样时刻，227 帧完整重组，19 帧因模拟缺片/坏 CRC 丢弃。丢帧画面明确标记，无伪造框。
- 既有 23 个稀疏标注框全部达到 IoU0.5；4 个选定目标在各自标注时刻没有换号。
  这是选定样本结果，不是全片准确率、召回率或 IDF1。
- GPU 检测加跟踪计算中位约 24ms；不包含真实 ARM 采集/传输/显示延迟。
- 33 项 Python 测试含 localhost UDP 实测；C 协议/时效守卫 132 项检查、跨语言黄金向量、远端邮箱与旧本地模式回归通过。

真实 PHY 协商、网口吞吐、实际采样率、端到端延迟和全部传感器共存尚未上板测试。
真实摄像头的小目标效果还受 320x240 输入限制；要进一步提高输入分辨率，需另做稳定 VGA 快照/缓冲区所有权设计。

第三方权重/依赖许可见原 README；lwIP 与 AMD XEmacPs 来自当前本地工具链，保留原许可与版权。
